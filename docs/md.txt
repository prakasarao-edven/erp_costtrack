CostBridge — Standalone Master Data BRD Addendum
Nov 4, 2026 · @AKM
1. Purpose, scope and decisions
CostBridge can run without an ERP once nine Wave 1 master data forms and a bulk upload exist. Today, every master record (projects, tasks, employees, equipment, items, rates and costs) is pulled from the ERP. This addendum adds local maintenance of the same records, so one product serves both integrated and standalone customers.
In scope
Wave 1 (go-live minimum): Project, Task/WBS, Employee, Equipment, Item, Store/Location, Labor Rate Card, Equipment Rate Card, Item Unit Cost.
Wave 2: Task Budget, Lookups (Craft, Grade, Equipment Class, UOM, Bonus Types), Work Calendar.
A bulk upload (CSV/Excel) for every entity, and a per-entity deployment mode setting.
Out of scope
Hour Types, approval rules, users/roles and tolerance settings. These already sit in the Setup module.
Customer/vendor masters beyond a name field, procurement, inventory on-hand balances and payroll.

 | Rules
MD-01: Natural keys must be unique across Source. Creating a Local P-1001 when an ERP P-1001 exists is rejected.
MD-02: In Hybrid mode, if an ERP pull brings a key that already exists as Local, the record goes to a Sync Conflict queue for an admin to merge or rename. It is not overwritten.
MD-03: Switching an entity from Local to ERP-synced needs a key-match run first. Matched records get their External ID; unmatched Local records stay Local.
MD-04: Local-only fields stay editable on ERP records (for example Default Store on an Item, or Foreman on an Employee). Each entity spec marks them LO.
MD-05: Transactions always reference the internal record ID, not the natural key. Renames and re-keys never break history.
3. Common design rules
These rules apply to all master forms, so each entity spec below lists only its own fields.
CR-01 Deactivate, never delete. A record used in any transaction can only be set Inactive. Inactive records disappear from entry dropdowns but stay visible in history and reports. Hard delete is allowed only for records never referenced.
CR-02 Effective dating. Rates and costs carry Effective From and an optional Effective To. Periods for the same key must not overlap. Entries are costed at the rate valid on the transaction date, not the entry date.
CR-03 Back-dated rate changes. If a rate changes for a period that already has approved entries, the system warns and lists the affected entries. A recost run is a separate, admin-only action.
CR-04 Audit trail. Field-level change history (old value, new value, who, when) on Rate Cards, Item Cost and Task Budget. Other entities keep created/updated stamps only.
CR-05 Status cascades. A Closed project blocks new entries on all its tasks. An Inactive employee or equipment cannot be added to a new plan or timesheet. Existing draft entries are flagged, not deleted.
CR-06 List screens. Every entity has a list with search, filters (Status, Source, plus entity-specific filters), column sort, export to Excel, and a Bulk Upload button.
CR-07 Form layout. Header fields at top, child records (tasks, rate lines) in a grid below. Save keeps you on the record; Save &amp; New clears the form. Required fields are marked; errors show next to the field.
CR-08 Code format. Natural keys are uppercase, no spaces, up to 30 characters. Each tenant can configure an optional auto-numbering prefix per entity (e.g. EQ-00001).

 | 6. Bulk upload
Bulk upload is the main go-live path, because standalone customers will load thousands of employees, items and tasks in one go. Every entity uses the same four-step flow.
Download template. An Excel file with one sheet per entity (a Project file also carries a Tasks sheet). It includes column headers, a hidden lookup sheet that drives dropdowns, and one example row.
Upload and validate. Every row is validated without saving: required fields, formats, lookups, duplicates within the file and against the database, date overlaps and parent-task references.
Review. The screen shows counts (New / Update / Error), with rows filterable by result. Errors can be downloaded as the same file with an Error column added.
Commit. Valid rows are saved in one transaction. The user picks All or nothing or Skip error rows.
Rules
BU-01 Match on the natural key: an existing key = Update, a new key = Create. A Mode column with Create / Update / Deactivate is optional.
BU-02 ERP-sourced records in the file are rejected, except for their LO fields.
BU-03 Load order is enforced: Lookups → Stores → Employees → Equipment → Items → Projects/Tasks → Rate Cards → Item Cost → Budgets. A file that references a missing parent fails with a clear message.
BU-04 Limit is 20,000 rows per file; larger files are split. Validation runs in the background, and the user is notified when it finishes.
BU-05 Every upload is logged with file name, user, time, counts, and the original and error files kept for 90 days.
BU-06 Task hierarchy: Parent Task Number goes in a column. Rows can be in any order; the loader resolves parents.
